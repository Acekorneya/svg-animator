4. PER-SCRIPT REVIEW: FALSE POSITIVES, FALSE NEGATIVES, UNSAFE COMMANDS & ASSUMPTIONS
-----------------------------------------------------------------------------

4.1 scripts/verify-architecture.sh
  - Unsafe / Destructive Commands:
    None. Strictly read-only file reads in Python 3.
  - Potential False Negatives:
    a) ARCH-03 (line 286): Checks Layer 3 operational sections for `dom_pattern`
       (`document.*`, `innerHTML`, `classList`) and three global UI functions
       (`openAccordionById`, `syncUIAfterHistoryRestore`, `syncAllRowsUI`), but
       does NOT scan Layer 3 sections for intra-module Layer 1 method calls on
       `this` (e.g., `this.renderList()`, `this.updateUIOverlay()`,
       `this.refreshAfterChange()`). If a Layer 3 method called `this.renderList()`,
       ARCH-03 would still report PASS.
    b) ARCH-07 (lines 369-374): Uses a narrow regex specifically targeting known
       exceptions in `stage.js` (`window.DataFlows.activeNodeIdx =`,
       `window.DiagramNodes.selectNode`, `window.DataFlows.updateUIOverlay`)
       rather than scanning all Layer 1 sections for any direct mutation of
       another module's state (`window.<Module>.list`, `.counter`, `.activeId`)
       or direct coordinate assignment on operational objects (`node.x = ...`).
    c) ARCH-10 (lines 492-498): Checks `if sym not in joined:` (substring
       presence in stripped code). A file that merely invokes `other.getState()`
       would satisfy `"getState" in joined` even if it forgot to define its own
       `getState()` method.
  - Potential False Positives / Tokenizer Edge Cases:
    a) `strip_js_comments_and_strings` (lines 71-74, 106-121): Recognizes regex
       literals only after single-character tokens `( , = : [ ! & | ? { } ; +`
       (missing keyword prefixes such as `return /.../`), and exits `REGEX_LIT`
       on the first unescaped `/` even inside a regex character class `[/]`.
       While none of the current 14 JS files hit this edge case, future regexes
       could desynchronize string stripping.

4.2 scripts/regression-harness.js
  - Unsafe / Destructive Commands:
    None. Uses only Node `fs.readFileSync` and `vm.runInThisContext` in memory.
  - Incorrect Assumptions / Unexecuted Bugs (Will Fail When Node.js Runs Stage 4):
    Because `node` is not installed on the LXC, `regression-harness.js` was not
    executed at runtime. Auditing Stage 4 (lines 308-333) against the actual
    production files reveals three bugs in the harness:
    a) Missing `window.buildFullSVG` and `window.serializeSVGForExport` globals:
       `StillExportStudio.buildStillRenderConfig` (`still-export-modal.js:318`)
       calls `window.buildFullSVG(...)`, and
       `AnimatedExportStudio.constructExportJobPayload` (`export-modal.js:104-105`)
       calls `window.buildFullSVG(...)` and `window.serializeSVGForExport(...)`.
       Those two global wrappers are defined inside `app.js` (`DOMContentLoaded`),
       which the harness does not load or alias onto `window`. Calling
       `buildStillRenderConfig` in Stage 4 will throw
       `TypeError: window.buildFullSVG is not a function`.
    b) Incorrect assertion path on `buildStillRenderConfig` return object
       (lines 316-317): `StillExportStudio.buildStillRenderConfig` returns
       `{ payloadState, rawSvg, fullTargetW, ... }` (`still-export-modal.js:325-337`).
       The harness checks `stillCfg.camera.motion` and `stillCfg.optical.type`
       instead of `stillCfg.payloadState.camera.motion` and
       `stillCfg.payloadState.optical.type`.
    c) Transitive dependency of `constructExportJobPayload` on browser `DOMParser`:
       In `export-modal.js:105`, `constructExportJobPayload` calls
       `window.serializeSVGForExport(rawSvg)`, which calls
       `SceneState.serializeSVGForExport` (`new DOMParser()` / `new XMLSerializer()`).
       In Node.js without `DOMParser`, calling `constructExportJobPayload` will
       throw `ReferenceError: DOMParser is not defined` unless `serializeSVGForExport`
       is either decoupled in production code or shimmed in Stage 4.

5. ASSESSMENT OF JAVASCRIPT REGRESSION HARNESS MOCKS (scripts/regression-harness.js)
-----------------------------------------------------------------------------
  a) Stages 1 & 2 (Lines 46-154):
     Genuinely test the real production code with virtually no mocking:
     - Stage 1 sets only `global.window = global` and directly exercises
       `SceneState`, `Effects.build`, and `AppCoordinator`.
     - Stage 2 adds only `window.addEventListener = function() {}` (needed
       because `stage.js` registers window resize/key listeners when defined) and
       genuinely tests `Stage` pure math, `NodePresets`, `DiagramNodes`,
       `DataFlows` (including orthogonal routing and waypoint insertion/removal),
       `Glows`, and `Ripples`.

  b) Stage 3 (Lines 160-299):
     Parses the actual `<input>`, `<select>`, and `<textarea>` elements from
     `internal/web/static/index.html` into an in-memory `controlElements` map so
     `ControlStateAdaptor.syncFromDOM` and `syncToDOM` read and mutate realistic
     initial values and checkbox states. However:
     - `window.syncUIAfterHistoryRestore`, `window.openAccordionById`, and
       `window.triggerAppRender` are stubbed as no-ops (lines 236-238), so
       Stage 3 tests operational state restoration in `HistoryManager.undo()/redo()`
       and `ProjectManager.applyStudioState()`, but does NOT test the DOM UI
       synchronization inside `app.js`'s `syncUIAfterHistoryRestore()`.
     - ProjectManager's `fetchProjectsList`, `fetchProjectById`, `postSaveProject`,
       and `postDeleteProject` are not called in Stage 3 (no `global.fetch` mock
       was wired up).

  c) Stage 4 (Lines 303-334):
     - `SceneState.buildFullSVG(fullState)` genuinely executes `Effects.build`
       and all four `injectIntoSVG` methods (`Ripples`, `Glows`, `DataFlows`,
       `DiagramNodes`) because those methods operate via string concatenation and
       `.replace('<!-- INJECT_CAMERA_RIG_ELEMENTS -->', ...)` without DOM APIs.
     - As noted in Section 4.2 above, the subsequent calls to
       `StillExportStudio.buildStillRenderConfig` and
       `AnimatedExportStudio.constructExportJobPayload` will fail when Node.js
       runs them due to the missing `window.buildFullSVG` /
       `window.serializeSVGForExport` aliases and the `stillCfg.payloadState`
       nesting.
